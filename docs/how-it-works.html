How it works

The architecture, the data model, and the design decisions behind them. If the tutorial is "how to use it", this is "why it's built this way". The authoritative version lives in DESIGN.md.

The core idea

You cannot draw a million images. You cannot even draw a million dots interactively in a comfortable way, and you certainly cannot read them. Every system that explores collections at this scale must show summaries that become more detailed as you zoom — a level-of-detail strategy, exactly like map software showing "12 restaurants" before showing each pin.

Image Atlas makes one firm commitment that everything else follows from: image positions are computed once and never change. A filter doesn't re-project the collection; it just hides points. This preserves the user's spatial memory — the single most valuable thing a map UI offers — and it makes the runtime cheap, because the only thing that varies per interaction is which points are visible, never where they are.

Two stages, strictly separated

Build is offline and slow; serve is online and instant and read-only. The serve stage recomputes nothing and will refuse to start on an incomplete bundle rather than silently regenerate it. This separation is the contract that keeps interaction fast: all expensive, stable work (decoding, layout, scoring, tiling) happens once, at build.

The data model

A built bundle is a self-contained folder:

fileholdswhy
manifest.jsonconstants count, zoom depth, thumbnail size, metadata schema
metadata.sqliteone row per image what SQL filters execute against; opened read-only
sprites.binraw map thumbnails a flat N×cell×cell×3 array — any thumbnail is an O(1) offset, memory-mapped
points/xy.npycoordinates fixed position of every image, normalized to [0,1]²
points/rep.npyscores per-image representativeness
points/z{z}_*.npytile indexes per zoom level: image ids sorted by tile, in compressed-sparse form, plus each tile's precomputed representative
previews/512px previews fetched only on hover/click

Image IDs are dense (0…N−1) and identical across every structure: row i of the SQLite table is row i of sprites.bin is index i of the coordinate array. That alignment is what makes a filter (a set of IDs) compose with a tile (also a set of IDs) by a plain boolean mask.

The runtime hot path

Every interaction reduces to this, and only this:

  1. Filter → run the SQL WHERE once, turn the matching IDs into a boolean mask of length N (1 MB per million images), cache it under a token.
  2. Viewport → for each visible tile, take its member IDs (a precomputed slice), keep those the mask allows, count them, and either emit them individually or choose one representative.

Nothing ever scans the whole collection during interaction. The unfiltered case is even cheaper — each tile's representative is precomputed at build, so panning around an unfiltered map is almost free. Measured at one million points: a filter is 40–140 ms (then cached to ~0), a viewport query is 0.4–15 ms.

How a region becomes one thumbnail

Within a tile that exceeds the threshold, the representative is chosen by: weighted center of mass (weight = representativeness score) → snap to the nearest real image → maximize score − 0.25·distance_to_anchor. Cheap, stable, and it lands on a real, central, typical image rather than empty space or an outlier. The full reasoning, including why this beats clustering, is in the tutorial.

Getting thumbnails to the browser

This is the one place the design was rebuilt after meeting reality. The obvious approach — pack thumbnails into big shared "atlas" images the browser downloads — fails at scale: thumbnails packed in build order have no relationship to map position, so a single zoomed-out view touches nearly every atlas page. At 400k images that was hundreds of megabytes per view over an SSH tunnel.

Instead, the server reads exactly the thumbnails a given view needs from sprites.bin and packs them into one small image ("sprite strip") on demand. A screenful costs ~100–400 KB regardless of collection size; the browser caches strips by ID, so panning back is free. Encoding a strip takes about a millisecond.

Deliberately simple choices

decisioninstead ofbecause
Canvas2DWebGL aggregation means ≤ a few hundred sprites are ever drawn; WebGL would be machinery without a payoff
SQLite (stdlib)DuckDB / a vector DB "return the IDs matching this WHERE over ≤1M rows" is squarely in SQLite's comfort zone; no extra dependency

grid aggregationk-means / HDBSCAN clustering the embedding already did the semantic grouping; a grid is exact, fast, and stable under filtering
boolean maskroaring bitmaps dense IDs make a plain numpy bool array intersect at memory speed; 1 MB/million is nothing
no-build frontendReact / a bundler three files, zero toolchain, trivial to audit and host statically

The throughline: do the hard work once at build, keep the runtime a thin layer over precomputed arrays, and let the browser render what it's told. That's what makes a million images feel boring to navigate — which is the goal.

This very demo

The live demo on this site has no backend at all. An export step bakes a small dataset into a single data file plus one sprite sheet, and a ~250-line shim re-implements the server's API in the browser using the same algorithms. The actual viewer code runs unmodified — proof that the frontend really is just a renderer over a small, well-defined API.
