1. Install

You need Python ≥ 3.10. Then:

pip install git+https://github.com/evoluchico/image-atlas

That installs the atlas command and its only two dependencies, numpy and Pillow. (You can also git clone the repository and use python -m atlas instead of atlas — everything below works either way.)

2. The one-command quick start

atlas run --images /path/to/your/images

This single command does everything:

  1. First run: it builds a dataset bundle in a folder next to your images (e.g. images_atlas/). This is the only slow step — every image is decoded once to make a small map thumbnail and a 512 px preview. Expect roughly 1,000–20,000 images per minute depending on your CPU and disk.
  2. Then (and on every later run, instantly): it starts a local web server and opens the map in your browser.

No metadata? No embeddings? It still works: you get a map laid out by visual similarity of color (a crude but serviceable default), and you can filter on path, width and height. The sections below add the good stuff.

Don't want to install anything yet? Generate a synthetic playground: atlas demo --out /tmp/demo, then atlas serve /tmp/demo/dataset. Or just open the browser demo.

3. Backend: preparing your collection for display

The backend has two separate stages, and the separation is strict by design: build (slow, offline, run when your collection changes) and serve (instant, read-only, run whenever you want to look). atlas run wraps both; you can also call them explicitly: 

atlas build --images DIR [options] --out DATASET     # prepare
atlas serve DATASET                                   # display

serve never recomputes anything. If a bundle is incomplete or from an older version, it refuses to start and tells you exactly what to rebuild — it will never silently regenerate data.

3.1 Metadata (makes the collection filterable)

Provide a CSV with one column containing filenames or paths, plus any other columns you like: 

filename,author,year,topic,license
photo_001.jpg,Alice,2019,protest,CC-BY
photo_002.jpg,Bob,2021,architecture,CC0
...
atlas run --images ./photos --metadata metadata.csv

The join column is detected automatically (matching by full path, filename, or filename-without-extension), column types are inferred (integer / real / text), and every column becomes filterable in the viewer with SQL. Images missing from the CSV simply get empty metadata; they still appear on the map.

3.2 Coordinates (makes the map semantic)

The position of each image on the map is fixed at build time. By default it is computed from raw color statistics — fine for a first look, but the map becomes far more meaningful if you supply 2D coordinates from an embedding projection, so that images that are semantically similar (same objects, style, composition) sit together. Supply them as a CSV: 

path,x,y
photo_001.jpg,4.27,-1.83
photo_002.jpg,-2.10,0.55
...
atlas run --images ./photos --metadata metadata.csv --coords coords.csv

Any coordinate scale works (they are normalized to the map square). The classic recipe to produce them — the same family of pipeline used by the Collection Space Navigator — is CLIP embeddings + UMAP: 

# pip install open_clip_torch umap-learn pillow torch
import csv, glob, torch, umap, open_clip
from PIL import Image

model, _, preprocess = open_clip.create_model_and_transforms(
    "ViT-B-32", pretrained="laion2b_s34b_b79k")
model.eval()

paths = sorted(glob.glob("photos/**/*.jpg", recursive=True))
embs = []
with torch.no_grad():
    for p in paths:                       # batch this for real datasets
        img = preprocess(Image.open(p).convert("RGB")).unsqueeze(0)
        embs.append(model.encode_image(img)[0].numpy())

xy = umap.UMAP(n_neighbors=15, min_dist=0.1,
               metric="cosine").fit_transform(embs)

with open("coords.csv", "w", newline="") as f:
    w = csv.writer(f); w.writerow(["path", "x", "y"])
    for p, (x, y) in zip(paths, xy):
        w.writerow([p, f"{x:.5f}", f"{y:.5f}"])

Embeddings are deliberately outside Image Atlas: they need heavy ML dependencies and a one-off computation, while the atlas itself stays lightweight. Any 2D layout works — t-SNE, PCA, or even hand-crafted axes like year × some score.

3.3 Excluding files

To build from an exact list (for example, excluding images your embedding pipeline flagged as corrupt), pass a text file of paths relative to --images, one per line: 

atlas run --images ./photos --files valid_files.txt --coords coords.csv

3.4 Build options

flagdefaultmeaning
--workers Nall cores parallel image decoding
--threshold N8 max images shown individually in a map cell before they collapse into a stack
--max-zoom Z10 depth of the aggregation grid (2Z×2Z cells at the deepest level)
--label-column COLnone derive hierarchical region labels from this metadata column (a density underlay is always written; see §4.2)
--cell PX48 size of the small map thumbnails
--preview-max PX512 size of the hover/detail previews
--name "..."folder name title shown in the viewer
--rebuild / --force— rebuild even if a bundle exists (run / build respectively)

3.5 Retiling & labelling (change settings without rebuilding)

Aggregation depth/threshold and the region labels all derive purely from the stored coordinates (and one metadata column), so changing them takes seconds, not a rebuild: 

atlas retile DATASET --max-zoom 11 --threshold 12
atlas label  DATASET --column topic       # (re)compute labels + density underlay

Use atlas label to add or re-derive region labels on a bundle you already built, or to try a different label column.

3.6 What the build produces

The bundle is a self-contained folder — copy it to another machine, archive it, or serve it from a NAS; it does not reference your original images at runtime: 

dataset/
  manifest.json     dataset constants (count, zoom depth, columns, ...)
  metadata.sqlite   one row per image; what SQL filters run against
  sprites.bin       all map thumbnails, raw, O(1) access by image id
  points/           coordinates, scores, and per-zoom tile indexes
  previews/         512px previews, fetched only on hover/click

4. What you are looking at

When the viewer opens you see a dark square — the map — scattered with thumbnails. Here is precisely what everything means:

  • The map is a fixed 2D space. Every image in your collection has one permanent position in it, given by your coordinates (section 3.2). Nearby images are similar; distance means dissimilarity. Positions never change — not when you zoom, not when you filter. This is what lets you build a mental map of the collection.
  • A lone small thumbnail is one image, drawn at its true position.
  • A larger thumbnail with a number badge is an "image stack" (an aggregate): a region that contains more images than can be sensibly drawn. The badge is the exact count of images in that region; the thumbnail is one real image chosen to represent them (how it's chosen — next section). A badge reading 2.6k means: there are 2,600 images here; zoom in or click to see more.
  • The status line (bottom left) shows the current aggregation level z and how many stacks/items are on screen.

4.1 How the image stacks are produced

This is the heart of the tool, and it is simple enough to state exactly:

  1. The map is cut into a grid. At zoom level z the unit square is divided into 2z × 2z equal cells ("tiles") — a quadtree: each cell splits into four at the next level. The viewer picks z automatically so that one cell is roughly one thumbnail wide on your screen (the thumbnail-size slider therefore also changes z).
  2. Each cell counts its images — only those that pass the current filter. Empty cells show nothing. Cells with at most threshold images (default 8) show them individually. Cells with more become one stack.
  3. The stack's representative is chosen in three steps:
    1. compute the cell's center of mass, weighting each image by its precomputed representativeness score (0.7 × local density + 0.3 × image quality — images from dense neighborhoods are more typical; broken or blank images score zero);
    2. snap that center to the nearest real image, so the anchor is never empty space;
    3. pick the image maximizing score − 0.25 × distance to anchor — i.e. the most representative image that is also near the middle of what it represents.

Two properties follow. First, counts are always exact — every image in view is in exactly one stack or shown individually, so badge totals always sum to the filtered collection size. Second, stacks respond to filters: filter to year = 2020 and each stack re-counts and re-chooses its representative among the surviving images only — while every position stays put.

Why not "real" clustering (k-means, HDBSCAN, …)? Because it isn't needed for legibility, it's expensive at scale, and it makes layouts unstable under filtering. The grid is dumb, fast, exact — and the embedding layout already did the semantic work. See How it works for the full argument.

4.2 Region labels & the density underlay

If the dataset was built with a --label-column (or you ran atlas label), the map also carries two things that make its global structure legible — what each area is "about" — rather than just what's in each cell:

  • The density underlay shows where images are concentrated: a soft magenta glow plus crisp contour lines (like a topographic map — each ring is a density level, tighter rings mean denser). Because the contours are drawn as vectors they stay sharp at every zoom, rather than blurring like a stretched image. It gives you the overall shape of the collection at a glance.
  • Region labels are text names floating over the map — the dominant theme of each area, drawn from your chosen column. They are hierarchical by zoom: zoomed all the way out you see only a few big, high-level region names; each time you zoom in, those areas reveal finer sub-region labels nested inside them. This is the same idea as a world map showing continents, then countries, then cities as you zoom.

How the labels are built and chosen, exactly:

  1. Each distinct value of the label column becomes a candidate. Values sharing a first keyword are merged into one clean region name (so "news brasil, cnn brasil" and "news brasil, globo" both become news brasil).
  2. Each region is placed at the spatial median of its images — a real, central spot, not empty space.
  3. Each region gets a level by how many images it holds: the largest themes are level 0 (shown when zoomed out), smaller ones get higher levels (revealed as you zoom). Bigger themes are also drawn in larger text.
  4. At any moment the viewer shows the most important labels that fit without overlapping — pan or zoom and the set updates, so you always see the "top features in view".

Labels describe the fixed geography of the whole collection, so they stay put when you filter (the regions don't move). Toggle them and the density underlay on/off in the side panel.

5. Frontend: exploring the map

actionwhat happens
drag pan around the map
mouse wheel zoom (anchored at the cursor). Zooming in splits stacks into smaller stacks and eventually individual images; zooming out merges them back
hover a thumbnail its 512 px preview and full metadata appear in the side panel
click a single image pins it in the side panel (hover stops overriding); click the map background to unpin
click a stack opens a contents grid in the side panel: every image inside that cell, most representative first, 60 at a time with a "Show more" button. Click any grid cell to inspect that image. This is how you look inside piles that are too dense to split spatially (e.g. near-duplicates)
Filters panel one control per metadata column, generated automatically: a multi-select for categories, a min–max pair for numbers. Pick values and the map updates — no query language to learn. The match count is shown; stacks re-count instantly; points never move. Clear all resets them. An Advanced: SQL drawer still accepts a raw WHERE clause (e.g. width > height) for power users
thumbnail size slider scales how large thumbnails are drawn (24–96 px) without changing the aggregation grid — purely a display preference; use the mouse wheel to change how finely the map is aggregated
Region labels / Density toggles show or hide the hierarchical region labels and the density underlay (§4.2); only present if the dataset was built with a label column
Shift + drag lasso-select a free-form region. The selection count appears in the panel; the map dims to the selection; Export CSV downloads all metadata + coordinates of the selected images (it composes with the active filter); Clear selection restores the previous view

A typical research loop: filter to a slice → glance at the map shape → zoom into an unexpected blob → click the stack → read actual images → lasso the region → export CSV → join the IDs/paths back into your analysis.

6. Remote & headless machines

Collections often live on a lab server. The atlas server binds to localhost only (it has no authentication), and on a machine with no display it skips opening a browser and prints exactly what to do — SSH port forwarding: 

# on your own machine
ssh -L 8765:localhost:8765 you@lab-server
# then open http://localhost:8765/ in your local browser

Already connected? Type ~C in the SSH session and add -L 8765:localhost:8765 without reconnecting. If you must expose it on a trusted LAN directly, --host 0.0.0.0 exists — but prefer the tunnel.

7. FAQ

A stack refuses to split, no matter how far I zoom.

Almost always that pile is exact or near-duplicate images: copies share (virtually) one embedding point, and no spatial zoom can separate identical coordinates. The badge is real information — "this exact image occurs 549 times" — and clicking the stack lets you browse the copies. If your data is merely dense rather than duplicated, deepen the grid: atlas retile DATASET --max-zoom 11.

Some images are gray squares.

Files that failed to decode at build time get a placeholder (and a quality score of zero, so they are never chosen as representatives). The build keeps them so that IDs stay aligned with your metadata; use --files to exclude them entirely.

How big can I go?

The runtime is benchmarked at 1,000,000 images: viewport queries are ~0.4–15 ms and any screenful costs a few hundred KB of transfer. Build time and disk are the practical limits — roughly 25 min and ~30 GB per 400k images (mostly the previews).

Can I change the map layout later?

Coordinates are fixed per bundle (that's a feature). To try a new projection, rebuild with a different --coords into a new output folder — your original bundle remains usable.
